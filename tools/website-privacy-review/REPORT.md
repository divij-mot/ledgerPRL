# Direct website custody and data-privacy review

Review date: 2026-10-09. This is a fresh-context, source-bound software review of the direct Ledger website, adapter and relevant installed dependencies. It is **not a security guarantee**, independent human audit, physical-device qualification, browser privacy certification or endorsement for valuable funds.

## Main assessment

The reviewed production flow has no private-key/seed input, private-key export, software-signing workflow or software-signing fallback. The browser obtains public account material and Ledger-produced signatures. It derives public addresses, constructs/validates transactions and verifies signatures. The intended custody boundary remains the Ledger's native signer.

The local-data requirement needs a narrower description than “public data is safe”: account derivation keys expose financial relationships, and complete already-signed bytes authorize broadcasting one exact payment. The browser intentionally retains safety/recovery information. It does not encrypt IndexedDB itself, does not establish a second security boundary against same-origin code or profile access, and cannot prove safe recovery after local state loss.

One low-severity UI privacy/context-reset issue was reproduced and fixed by the coordinating implementation: recipient, amount and fee previously survived Close account in module memory and reappeared in the next account's Send view. The current source resets these active fields. The independent probe passes Close/reopen, different snapshot account, public-account import and network-change controls. It also verifies that clearing the optional saved watch copy leaves all payment journals unchanged.

## Findings and resolution

### P1 — Ephemeral payment form survives account close: resolved

- Original location: `apps/companion/src/main.ts`, module `form` plus `bind()`'s `disconnect` handler.
- Reproduction: load the public example watch snapshot; set public canary recipient, amount and fee; invoke the actual Close account handler; reopen a snapshot and render Send. The account/history were cleared, but all three form values remained.
- Impact: another person using the still-open page could see the prior recipient/amount; a different account could inherit stale payment inputs. No automatic payment, signature, persistent storage or network transmission occurred in this probe.
- Current fix: `clearPaymentForm()` is called for close and account-context changes. `ui-retention-original.json` records the original observation; `ui-retention.json` records the passing final controls. JavaScript assignment does not guarantee erasure from the browser heap, swap, crash dumps or snapshots.

### P2 — Generic cryptography is bundled, but no private signing workflow was found

`packages/sdk/src/keys.ts:derivePublicKey()` constructs `HDKey` using only publicKey and chainCode. The deterministic probe intercepts real `HDKey.deriveChild()` and observes null private keys before/after both derivation levels for both branches and representative indices. Exact account JSON validation rejects extra seed, mnemonic, privateKey, xprv, password and prototype-key fields. The adapter rejects an extended-private version marker.

A fresh production Vite build nevertheless contains generic `HDKey.fromMasterSeed`, private-extended-key and signing support from `@scure/bip32`/`@noble/curves`. That is dependency code, not evidence of wallet key exposure or a production call to software signing. Replacing audited general-purpose libraries with custom cryptography merely to remove these functions would not be an appropriate response. Precise documentation should say **no software-signing workflow or private-key input/fallback**, rather than literally claiming no signer implementation exists in runtime bytes. The current README has been corrected accordingly, and SECURITY.md now qualifies the import boundary.

An import validator must read an accidentally selected file before it can reject its contents. Therefore “a user can never put secret bytes in browser memory” is not an enforceable claim for a public JSON import surface. No seed, PIN or private wallet file should be selected. The intended production flow neither requests nor derives private signing material.

### P3 — Dependency error-reporting hooks exist; no default uploader found

The pinned WebHID dependency calls `@sentry/minimal.captureException()` on discovery/open errors in `api/transport/WebHidTransport.js` and `WebHidApduSender.js`. The bundle contains Sentry hub/minimal/utils. The app does not configure a Sentry client/DSN/upload transport. DMK's builder starts with zero logger subscribers, and `connectLedger()` adds none.

`dependency-errors.mjs` bundles the actual pinned browser Ledger adapter and dependencies, presents a fake HID API that rejects its device-picker request, and observes a Sentry capture hook with **no configured client and zero fetch/WebSocket/beacon attempts**. This is one bounded default error-path check, not coverage of every dependency path. A separately initialized same-origin Sentry client could change behavior, another reason to require a dedicated origin without unrelated scripts. Ledger manager and update-WebSocket URL constants are also bundled; their presence is not proof they are contacted by the current wallet flow. Production CSP restricts connections to the same origin.

## Requests, rendering and logs

- Hosted public reads use a same-origin POST to `/api/indexer/read` with exactly network, consent and a fixed allowlisted read path. Browser fetch uses `credentials: omit`, `redirect: error`, `cache: no-store`; public account keys/ranges are not request fields. Consent is session-memory state and is reset at account changes.
- Proxy `indexerProxy()` requires exact Host/Origin, the custom header, POST and bounded exact fields. Upstream destinations are two fixed HTTPS Blockbook bases. Addresses/txids necessarily appear in upstream URL paths, so upstream/proxy infrastructure may log them even when the application does not.
- Broadcast uses a separate `/api/indexer/broadcast` body and never automatically retries. An unconfirmed response leaves ambiguity and reservations. Server-side shape/txid checks are not fresh device approval, and cannot prevent anyone already holding signed bytes from broadcasting elsewhere.
- The page uses template `innerHTML`, but free-form text/form/error strings go through `e()` escaping. Remaining dynamic strings derive from bounded numbers, fixed enums, validated hex or locally encoded addresses. No reviewed unescaped arbitrary third-party HTML sink was found. This is a manual bounded source review, not a universal XSS proof.
- Account metadata, balances, recipient and activity are deliberately rendered and therefore visible to screen observers and eligible extensions. No seed UI exists. Closing the account hides account/history state but is not a secure-memory wipe and deliberately does not delete durable payment records.
- App frontend source has no console logging of account/signature/transaction values. Hosted server logs only generic startup/listen/failure messages. Indexer errors are fixed generic strings, not reflected upstream bodies. The local bridge can return bounded diagnostic messages to the frontend; the frontend escapes them.
- `web-server.ts` serves only an in-memory snapshot of allowlisted static assets and two proxy APIs, with strict same-origin CSP, anti-framing, no-referrer and no-store on HTML/API/errors. No configured analytics, cookies, account database, backup upload or service-worker registration was found. Vite dev/preview is explicitly a separate loopback development workflow, not the production hosting boundary.
- Caddy's example disables request access/error logging and strips client Cookie/Authorization and forwarded identity headers upstream. This does not prove a real reverse proxy, hosting provider, network or CDN is configured accordingly.

## Local integrity versus privacy and hostile-host limits

1. `validateStoredJournal()` checks bounded schema, states, canonical bundle structure, reservations, paths and raw-transaction correspondence. Ownership/signature checks remain at signing/import/broadcast boundaries. Its bounded deterministic cache avoids repeatedly decoding identical byte strings. This is useful integrity validation, not authenticated/encrypted storage.
2. A hostile same-origin script, extension with sufficient privileges or compromised profile can read, coherently rewrite, roll back or delete records. A schema-valid older or missing row cannot be proved fresh using only that same browser's storage. UI approvals and host validation are bypassable by a malicious served app.
3. Same-origin IndexedDB atomic mutations coordinate cooperating tabs of one browser profile. Separate profiles/origins/computers do not share reservations. Browser eviction/private-mode loss/reinstallation can remove recovery history. Restoring an incomplete backup is not proof that no signature was previously made.
4. Retaining exact signed bytes and uncertain reservations is justified safety state. Deleting it to minimize data can erase knowledge of a spendable transaction that a node has never seen. Archived confirmation records therefore retain locks and bytes. The app's newly added `removeSavedSnapshot()` deletes only `public-cache:last-snapshot`; it does not clear journal rows, an open account, downloaded files or all heap copies.
5. Hardware approval does not make browser metadata private. A malicious host can request harmful payments, misrepresent chain data, substitute UI labels, or broadcast already-signed transactions. The trusted-device screen and correctly functioning authentic firmware remain essential; neither was exercised here.

## Reproducible verification and boundaries

Run from repository root, using the already installed pinned dependencies:

```sh
node --import tsx tools/website-privacy-review/review.mjs
node --import tsx tools/website-privacy-review/ui-retention.mjs
node --import tsx tools/website-privacy-review/dependency-errors.mjs
node --import tsx --test apps/companion/test/public-source.test.ts apps/companion/test/web-server.test.ts apps/companion/test/storage-integrity.test.ts
```

- `review.mjs`: 9 deterministic checks pass; fresh Vite production build is `write:false` and does not overwrite deployment artifacts. Main module graph: 341 modules; backup worker: 27; union: 342. No server/bridge, CLI/Snap/MetaMask, tests/fixtures or legacy SDK device implementation appears in either browser graph. Public synthetic sample JSON remains available only in the separate local development flow; production host refuses its route.
- `ui-retention.mjs`: actual current UI handlers with a modeled DOM/atomic-storage boundary; fixed context clearing and narrow optional-cache deletion pass. No device, real IndexedDB or real browser involved.
- `dependency-errors.mjs`: actual pinned DMK/WebHID library under a mocked rejecting HID API; default error capture does not produce network calls or a configured telemetry client.
- Focused existing source/server/storage suite: **31 passed, 0 failed**. HTTP tests use loopback fixtures and injected synthetic upstream responses, not a public indexer.
- `results.json` contains exact emitted chunk hashes, complete main/worker module graphs and reviewed source hashes. `focused-tests.log` preserves the test output. Hashes identify this working source, not a clean published commit or qualified release. Concurrent later source changes require a rerun.

No native firmware/emulator lane was executed, retried or rerouted. No physical Ledger, real seed/key, real funds, live RPC/indexer, real broadcast, browser upload, existing profile/CDP, extension installation, public deployment, credentials or vendor contact was used. Full loaded-browser WebHID/IndexedDB/CSP/clipboard behavior, hardware trusted review, actual infrastructure logging, supply-chain authenticity and independent security audit remain unverified.
