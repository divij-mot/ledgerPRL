## Findings and disposition

1. **Setup instructions were stale.** README and Live App/companion guides described public-indexer startup and omitted native build prerequisites. Updated the four approved guides to `npm run setup:light` followed by `npm start`, exact loopback origin, local stdio/native profile behavior, remembered public account lifecycle, build prerequisites and hardware-only installation gate. Development Vite/preview now also includes native middleware; a static server alone does not.
2. **Public and backup import did not start/remember local sync, and import copy directed users toward address disclosure.** Reported to root/wallet reviewer. Re-reviewed the resulting `runAccountRestore`, `rememberLocalAccount`, `resumeLocalAccount` and `LocalSession` ownership code. Import/reload/device approval semantics remain distinct; closing an account retains payment recovery while clearing automatic-open preference. Focused lifecycle tests pass.
3. **Resolved: unsupported nonzero mainnet account presented the local Sync action.** Re-reviewed the final `lightCard` and `startLocalSync` guards: both require mainnet account 0 for local sync. Other mainnet accounts use the explicitly consented public-source path. The wallet reviewer’s final actual-main regression for this behavior passed in its 13-case discovery/lifecycle suite.
4. **Local fees lack the official desktop's network estimates.** Exact manual total fee, size, dust and pinned relay-minimum validation are present; local mode correctly does not fabricate confirmation-speed estimates. A convenience “Use minimum” control is optional polish, not implemented by this reviewer. Any such action must preserve recipient amount and manually selected inputs, recalculate change/size, and pass final `preparePayment` policy validation. The current docs explicitly disclose the limit.
5. **History has a narrower schema.** Pagination, confirmations and transaction IDs are present; timestamps and general historical transaction fees are absent. These remain normal usability/parity gaps, not evidence of missing ledger-signing capability. The docs now distinguish them from implemented behavior.
6. **Native dependency notices extend beyond browser inventory.** Upstream source pin/build tags are recorded and the helper links official wallet/Neutrino/XMSS/ZK libraries. Browser notices cannot qualify this added dependency graph for distribution. The Live App guide now calls out native license preservation and the project's still-unselected license. This local build is not a public release qualification.
7. **Device app identity changed.** Current mainnet Wallet API request names `Pearl`; prior physical evidence used `Pearl Dev`. The docs do not suggest the old device app will satisfy the renamed request. Installing/rechecking Pearl 0.1.0 remains an owner-approved hardware step.

## Architecture and remaining qualification

The product is one local server plus one watch-only native helper using the existing browser/Ledger signer. It does not add a second GUI, hot-wallet key entry, external RPC listener or cloud dependency to the default flow. The standalone WebHID and optional public-indexer/authenticated-node compatibility paths still exist behind the shared wallet; they should not be described as required components of the local Discover flow. The dependency graph's separate host entries keep WebHID out of Discover and Wallet API out of the ordinary browser entry.

This review does not independently certify full synchronization, restart/rescan, native proof validation, funded send/relay/confirmation, or signer behavior. Root's separately recorded native run must carry its exact helper/source identity. Retain explicit hardware gates for the renamed Pearl binary, trusted address/amount/fee review, signing/rejection/disconnect/recovery via the real Ledger Wallet bridge, supported-input maximums and non-Nano-S-Plus devices. The user must approve each real payment when awake; no funded trial was performed here.
