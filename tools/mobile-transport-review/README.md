# iPhone / optional Ledger Wallet transport review

Source review and official-client mock bridge tests, 2026-10-10. The pinned [Ledger Wallet mobile 4.23.0 release](https://github.com/LedgerHQ/ledger-live/releases/tag/live-mobile%404.23.0) points to `abed962b08ca4b746f20192b28ce5b6c06a6c6a4` and was published October 2. This confirms a published source release, not the installed version on any particular phone or universal App Store rollout. No phone, Bluetooth radio, device, account or funds were accessed. No Android SDK or emulator was installed.

## iPhone path supported by the inspected source

Stock iPhone Safari does not expose Web Bluetooth. A plain website cannot supply the native BLE link just by changing permissions or a manifest. The [Web Bluetooth implementation status](https://github.com/whatwg/bluetooth/blob/main/implementation-status.md#safari) distinguishes native support from third-party native bridges. Pearl's supported integration target here is the hosted `/live.html` page inside Ledger Wallet's React Native WebView, whose host supplies BLE; desktop `/` remains the standalone WebHID entry.

The pinned mobile [WalletAPIWebview](https://github.com/LedgerHQ/ledger-live/blob/abed962b08ca4b746f20192b28ce5b6c06a6c6a4/apps/ledger-live-mobile/src/components/Web3AppWebview/WalletAPIWebview.tsx) uses the shared Wallet API server. Its [helpers](https://github.com/LedgerHQ/ledger-live/blob/abed962b08ca4b746f20192b28ce5b6c06a6c6a4/apps/ledger-live-mobile/src/components/Web3AppWebview/helpers.ts#L727) register `device.transport` by navigating to DeviceConnect with the requested app name. There is no iOS-specific rejection in that handler or the common raw device handlers. The [DeviceConnect screen](https://github.com/LedgerHQ/ledger-live/blob/abed962b08ca4b746f20192b28ce5b6c06a6c6a4/apps/ledger-live-mobile/src/screens/DeviceConnect/index.tsx) selects a device and uses Ledger's app-opening action; omitting a name defaults to BOLOS. Pearl supplies its exact network-specific name, with `Pearl` for mainnet. It does not supply `appVersionRange`, so the optional host range check does not prevent a 0.1.1 app with the same name. Pearl's own protocol/network/account checks remain mandatory.

The existing hosted manifest originally declared desktop and Android only. That omission was this project's prior scope, not evidence of an upstream ban on iOS device transport. Adding `ios` expresses the intended platform; it does not prove BLE firmware or physical qualification. The earlier Pearl build disabled Bluetooth in its Makefile, which is a separate device-side blocker. The [BLE build evidence](../ble-review/README.md) records that change separately; this report does not claim physical installation or radio qualification.

## Pinned mobile manifest-loading steps

1. Open **Settings → Developer**. In this mobile source the Developer card is present directly; the desktop ten-version-taps procedure is not needed. Do not confuse this with the Manager Developer Mode option under Experimental features.
2. Enable **Allow debug apps**, then open **Load Platform Manifest** (screen title **Load Manifest**).
3. Copy the canonical hosted manifest's JSON contents. Use the top Paste control, then Add. The source parses JSON; pasting only the URL is not equivalent.
4. Tap Pearl under **Loaded Manifests**, or its locally loaded Discover entry. The manifest must point to the hosted `/live.html` entry and retain the exact origin and narrow Wallet API permissions.
5. Connect from that page using the host's device picker and the matching installed Pearl app. The source supports this path; actual iPhone pairing, app opening and transaction review still require physical qualification.

These instructions come from the pinned [Settings screen](https://github.com/LedgerHQ/ledger-live/blob/abed962b08ca4b746f20192b28ce5b6c06a6c6a4/apps/ledger-live-mobile/src/screens/Settings/index.tsx#L114), [Developer screen](https://github.com/LedgerHQ/ledger-live/blob/abed962b08ca4b746f20192b28ce5b6c06a6c6a4/apps/ledger-live-mobile/src/screens/Settings/Developer/index.tsx), [CustomManifest screen](https://github.com/LedgerHQ/ledger-live/blob/abed962b08ca4b746f20192b28ce5b6c06a6c6a4/apps/ledger-live-mobile/src/screens/Settings/Developer/CustomManifest.tsx) and English locale labels. Public catalog publication is separate from developer loading.

## Bridge, packet and lifecycle boundaries

Ledger pins React Native WebView 13.16.0. Its [iOS postMessage implementation](https://github.com/react-native-webview/react-native-webview/blob/v13.16.0/apple/RNCWebViewImpl.m#L1111) dispatches a data-only window MessageEvent, whose default origin is empty and source is null. Ledger's pinned patch changes TLS test support, not this reply shape. Pearl accepts that native shape and rejects non-null web peers or foreign origins. The official Wallet API transport also listens on document for Android replies and sends via ReactNativeWebView.postMessage. No weakening of the existing reply filter was necessary.

The bridge sends a complete APDU as hexadecimal and receives the complete response including status words. Native host transport handles BLE packet fragmentation; the browser should not truncate APDUs to the BLE MTU or implement a second fragmentation layer. The source path is the common `openTransportAsSubject` forwarding raw exchange through `withDevice`. Pearl serializes exchanges, uses bounded open/exchange/close waits, preserves a winning final-signature response, and refuses reconnect when old cleanup is unresolved. These properties remain important because the host uses a shared transport ID.

The updated normal-CI `wallet-api.test.ts` passes **19/19** tests. The actual official client runs against three explicit synthetic bridges: desktop window, iOS data-only window and Android document. Cases assert exact app name, capabilities, rejection of forged origins/non-null mobile sources, untouched `e000` continuation status, an opaque 258-byte response, cleanup and fresh reconnect. Existing cancellation, late open/exchange, unresolved cleanup and verified-final-result tests remain. This proves JavaScript bridge framing and guards under mocks; it does not test radio fragmentation, iOS WebView persistence, mobile host UI, pairing, firmware installation or physical BLE. Source hashes and test output (`bridge-tests.txt`) are retained alongside this report.
