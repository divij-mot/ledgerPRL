# Hosted deployment, privacy and resource review

Review date: 2026-10-10. Scope: the new stateless Vercel adapter, static publication boundary, origin/body validation, request and concurrency budgets, browser account cache, QR camera/image boundary, jsQR provenance and shipping notices. This report distinguishes source/unit verification from actual hosted preview and native-phone qualification.

## Findings

1. **P2, fixed: imported QR image output dimensions were bounded too late.** The original `readQrImage` called `createImageBitmap` with only `resizeWidth: 1280`, then checked the resulting pixel count. A narrow, tall compressed image could cause extreme height upscaling before that check. Root changed the decode request to explicit 1024×1024 output dimensions, retaining the 8 MiB input and post-decode pixel bounds. Source fix verified. Root's real-browser qualification record covers native PNG/ImageBitmap decoding of 320×320 and 640×320 QR fixtures and synthetic canvas MediaStream playback through an actual video element under production CSP, including ended tracks. `qr-browser-result.json` source and CSP hashes match the reviewed current files. This evidence uses synthetic media, not a physical camera or Android permission prompt.
2. **P2, fixed: the newly shipped jsQR dependency was absent from shipped notices.** `jsqr@1.4.0` is Apache-2.0, but the previous public notices lacked its package/license attribution. The QR module's vendor-provenance pointer also had no matching QR reference in the vendor records. Independently verified the corrected notices contain the jsQR package header and complete installed LICENSE verbatim; the vendor README now identifies the pinned Ledger QR scanner source, and the provenance row's adapted SHA-256 matches the current `qr-reader.ts`.
3. **P2, fixed before deployment: automatic outbound fetch tracing was enabled.** The first complete Vercel prebuild set `shouldDisableAutomaticFetchInstrumentation: false` in both functions. Although application code logs no bodies, outbound indexer URLs contain wallet addresses/transaction IDs and are unsuitable for automatic fetch traces. The public `VERCEL_TRACING_DISABLE_AUTOMATIC_FETCH_INSTRUMENTATION=1` flag is now configured for build/runtime, the hosted build guard rejects missing/disabled privacy flags, and both the actual Node-builder replay and rebuilt complete CLI output set the tracing-disable property to true. `prebuilt-validation.json` records the final artifact checks. This removes automatic fetch instrumentation, not ordinary infrastructure request metadata. [Vercel tracing](https://vercel.com/docs/tracing).

**No unresolved P0–P2 issue was established in this deployment review.** Production `https://pearl-ledger-wallet.vercel.app` passed 17 read-only HTTPS checks. All 15 deployed public files exactly match the final prebuilt checkpoint, totaling 2,222,424 bytes. Audited source files remained unchanged through verification. Source/evidence fingerprints are recorded in `deployment-source-hashes.json`.

## Hosted boundary

Only the browser `dist` directory is published as static content. A build-time allowlist rejects unexpected top-level files, source maps, symlinks, non-hashed asset names and excessive sizes, and Vercel builds require both raw-helper and automatic-fetch-tracing disable flags. Two functions reuse the existing `indexerProxy` through the new bounded raw adapter. Actual local Vercel Node-builder outputs contain four files each and no native program, local-light module, wallet database, tools or account profile; evidence is in `../hosted-adapter-review/node-builder.json`. The complete CLI build adds each function's `.vc-config.json`, for five files per function.

Production requires one explicit HTTPS `PEARL_WEB_ORIGIN`. A preview may bind to only its platform-supplied `VERCEL_URL` under `VERCEL_ENV=preview`. Host/Origin equality, singular raw headers, POST, same-origin fetch metadata, uncompressed JSON, canonical Content-Length, actual byte length, valid UTF-8, 128 KiB request maximum and bounded upload time are enforced before upstream work. `NODEJS_HELPERS=0` disables Vercel's pre-reading helpers at build time; a pre-parsed/consumed request fails closed. The body is replayed without JSON reserialization.

The existing proxy allows only fixed Pearl mainnet/testnet2 hosts and fixed data paths, rejects account-key-like address strings and unknown fields, disables redirects and requires disclosure consent. No request-supplied URL, private node, local helper or RPC credential reaches a fetch target. Broadcast is one-shot and preserves ambiguous failure, with no automatic retry. Generic error messages do not reflect request or upstream contents. A same-origin gate is a browser boundary, not global authentication or an abuse quota against arbitrary HTTP clients.

There is no application database, server wallet profile/history cache, cron, analytics integration or application body logging. Bounded request buffers and a per-instance active counter are transient processing state. Infrastructure may retain ordinary request metadata, and the explicitly selected indexer receives the requested public addresses. API paths themselves carry no addresses or transaction bytes. The existing localhost Discover manifest remains unchanged and outside the static output.

The separate `apps/companion/ledger-live.hosted.manifest.json` targets exactly `https://pearl-ledger-wallet.vercel.app/live.html`, lists `platforms: ["desktop", "android"]`, confines domains to that origin and requests only `wallet.capabilities`, `device.transport`, `device.exchange` and `device.close`. It remains private/debug, with no catalog approval or native Pearl Accounts claim. The distinct `pearl-hosted` ID and cache-busting value 1 should stay stable for hosted storage continuity; they do not migrate the local app's browser state automatically.

`validate-manifest.mjs` verifies the pinned installed Ledger Wallet 4.23.0 renderer SHA-256, extracts its actual manifest-schema module and actual pure Zod dependencies, and evaluates them without bootstrapping Electron or opening user state. Only the schema module's unrelated exported currency-map imports are stubbed. Both local and hosted manifests pass. The obsolete singular `platform` field and a `platforms: ["mobile"]` variant fail; the actual enum is `ios`, `android`, `desktop`. Exact URL/domain/four-permission assertions also pass. Evidence: `manifest-validation.json`. Schema acceptance does not qualify the physical Android host or constitute importing/publishing the app; neither action was performed.

## Resource and free-tier efficiency

- **Hostile concurrency, tested:** 17 simultaneous requests cause exactly 16 upstream calls; request 17 gets 429. Disconnecting all 16 responses aborts every upstream, releases all slots and permits a fresh successful request. This cap is per function instance, not across all autoscaled instances.
- **Empty-account discovery, tested:** exactly 46 upstream reads: 40 address-history reads and two three-read tip checks. It makes no unused-address UTXO requests and has at most five address calls in flight.
- **Uncached fee group, tested:** six public non-address reads, with at most three concurrent. Quotes have a two-minute TTL. The final scheduler refreshes approximately 15 seconds before expiry only while the visible, unprepared send-amount step is active; it stops for hidden pages/prepared payments, defers while busy, and still allows explicit manual refresh. There is no address disclosure in these fee/status reads. Combining a fresh empty account scan and uncached quotes is 52 public reads. Used accounts require additional bounded reads.
- Hosted account restoration can display a local cached view but resets complete-scan, source validation and address/device approvals. Sending remains gated on fresh discovery and pre-signing checks. This display cache does not become server state or spend authorization.
- The local-only refresh timer is gated out in hosted mode. There is no hosted background full-scan polling loop. HTML and API data are `no-store`; content-hashed assets receive immutable caching. The prebundled Node handler is approximately 58 KiB. Final prebuilt static output contains 12 hashed assets plus the two HTML entries and notices, totaling **2,222,424 bytes** before transport compression. The QR decoder is in separate lazy chunks. Every static file byte-matches the current client build.

The configuration is suitable for a small stateless Hobby deployment but does not guarantee zero charges or protect the whole account's quotas from public traffic. Root owns actual plan, limits and deployed-project verification. No paid integration is configured by this change.

## QR and browser privacy

QR decoding is lazy-loaded, runs on local canvas pixels and does not upload images or frames. Camera access occurs only after the scan action, requests no audio, scans frames at 400 ms intervals with a maximum 640-pixel side and stops after 30 seconds, success, failure or cancellation. A late permission result is explicitly stopped after cancellation. The final camera policy allows only `camera=(self)`; microphone, location and payment APIs remain disabled.

Payment QR parsing accepts only a network-valid address or bounded `pearl:` request with nonduplicated supported fields and a positive exact decimal amount. It rejects foreign URL schemes, hosted authority syntax, fragments, duplicate amount fields, unsupported request fields, wrong-network addresses and unsupported precision. A QR updates the visible form only; account/network/page ownership is rechecked after asynchronous decoding, and Ledger review plus separate broadcast approval remain required.

Supply verification independently downloaded the official npm jsqr 1.4.0 archive, matched the exact lockfile SHA-512, and compared all 17 installed package files byte-for-byte: zero mismatches. The package has no runtime dependencies. See `jsqr-integrity.json`. Source inspection found no decoder network, browser storage, `eval` or `new Function` calls. This is source/integrity evidence, not a claim that every decoder algorithm has been formally verified.
