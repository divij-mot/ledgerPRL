# Final release-fix host review

Scope: production changes after `e6b0ff1` in the companion main flow, pending monitor, Bitcoin-derived adapter and journal cancellation helper, plus recipient validation. The frozen replay and source hashes are recorded in `release-fix-wallet-source.json`. No unresolved P0–P2 finding remained in this bounded scope after the corrections below. This is an independent AI source review with finite mock-based tests, not a professional audit, exhaustive concurrency proof or physical-device qualification. No real account state, hardware signature, broadcast, funds or private account data was used by this reviewer.

## Findings and corrections

- The first pending-monitor implementation stopped tracking outgoing payments at their first confirmed history entry, before the journal's six-confirmation archival threshold. The correction retains owned submitted/unknown records until archival, compares a mined/settled confirmation bucket, and performs a fresh full scan at meaningful changes rather than every block.
- The first correction still excluded owned unarchived records whose normal sync/restored history was already mature. The final candidate rule keeps them until reconciliation, so reopening after six confirmations cannot leave a submitted record stuck. A dedicated actual-main regression covers this case.
- Manual public/local payment-status refresh now combines user cancellation with the same five-minute account-scan deadline used elsewhere. Each public request also retains its existing 20-second deadline and bounded response parsing; discovery retains its existing address/history/byte limits.
- The signing path previously committed the initial signing attempt before abort/journal/freshness checks outside its catch. These post-commit checks now share one ownership-checked cleanup helper with adapter no-result failures. Only the unchanged initial attempt with no staged/saved complete bytes is reset and discarded. Recovery and concurrent record modifications are retained.

## Reviewed behavior

The portfolio headline uses existing total owned unspent balance, including unconfirmed change. Pending and immature information remain separate; the misleading whole-input pending-payment banner is removed. Send's available balance and input eligibility are unchanged. This matches the inspected pinned Ledger account headline calculation, while Pearl retains its stricter confirmed-input spending policy. No synthetic optimistic balance arithmetic was added; see the separate pinned Ledger balance source report.

Hosted Sync now starts public discovery directly and records the existing public-source preference after successful sync. Local default mainnet account zero retains native synchronization. The button changes neither signing nor broadcast authorization. Recipient Continue, QR parsing and final payment construction continue sharing the canonical SDK address decoder; new adversarial length/checksum/network/version/padding tests found no production validation gap.

Manual status refresh acquires new account discovery before reconciliation and invalidates old spend authority while checking. Its owner, source, selection and abort guards are rechecked after asynchronous boundaries and inside the atomic journal callback. The local scan merges native persisted last-used bounds with journal recovery bounds. Missing, contradictory or unavailable source data does not release signed inputs or erase exact signed bytes. Reorg reconciliation can remove archived status without releasing reservations.

Pending monitoring is read-only: eligible visible public-account views poll known transaction IDs, at most four per cycle with rotating selection, an initial five-second check and subsequent absolute minute deadlines. Rerendering the same view does not postpone deadlines or multiply requests. New known transaction IDs may bring the next check forward. Hidden, busy, receive and unsigned/signing review contexts disable it; owner/selection changes abort active work. Reads only trigger full discovery on changed status, and all apply/storage stages retain current-context guards. Incoming history-only entries stop at first mining; owned submitted/unknown records continue to six-confirmation archival. Archived records are not continuously polled for future reorgs; manual refresh remains the recheck path. No monitor path invokes the device or broadcasts a transaction.

The adapter's `SigningFailedWithoutResultError(cause)` means that invocation produced no complete independently verified app result; partial device signatures may exist. An abandoned exchange response cannot later invoke the verified-result callback. Complete bytes are assigned before persistence and remain available after callback failure, timeout, final-ACK failure or cancellation. The host preserves returned/staged/saved complete results, historical recovery ambiguity and changed ownership. Generic unclassified UI failures do not acquire this type's cleanup authority. See `signing-result-adapter-review.md` and the independent product signing-boundary report for detailed cases.
