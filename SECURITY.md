# Security status and boundaries

This project is development software. It has not passed an independent human audit or Ledger functional/security review. Physical qualification is limited to the specific Nano S Plus/build/OS observations recorded in the evidence; it is not broad hardware validation. Do not put valuable funds on development accounts. Test success does not establish security parity with Ledger's Bitcoin application.

## Custody model

- The Ledger derives PRL keys from its existing securely initialized seed. The companion never asks for recovery words, exports private keys, unlocks a hot wallet, or signs in software.
- The native app validates a bounded committed PSBT transaction, independently derives all owned inputs/change, computes BIP341 digests, and requires trusted on-device review.
- The native signing primitive is the Ledger SDK's secp256k1 BIP340 implementation. The current device app adapts pinned Ledger Bitcoin 2.5.1 C code for PRL-specific network, monetary, path, address and lifecycle policy. The earlier Rust prototype is retained as historical reference. Borrowed upstream code does not transfer Ledger approval or security assurance to this port.
- Device permission metadata restricts derivation to purpose 86 and the selected coin type. Network-specific binaries, account/path validation and clear network labels provide context. Pearl's ordinary transaction digest has no additional chain identifier.
- Only no-script BIP86 P2TR owned inputs/change and SIGHASH_DEFAULT are supported. No annex, script-path signing, external inputs, arbitrary digest/message signing, nondefault sighash, or blind-sign fallback exists.
- This is conventional elliptic-curve custody, not post-quantum custody. XMSS/state restoration and P2MR spending are outside this version.

## Host and backend trust

The wallet is watch-only until Ledger approves signing. Local mode uses the pinned official Pearl wallet/Neutrino implementation and native proof verifiers, inheriting upstream SPV assumptions rather than full-node validation. Hosted mode trusts fixed public-indexer chain/history answers; raw transaction, script, genesis and consistency checks detect some contradictions but cannot establish complete history. The Ledger verifies what is being signed; it does not authenticate the host’s current chain view.

Hosted **Sync** is the explicit action that starts public indexing; its successful choice can be remembered. Local mode retains its separate public-source preference. Public services are fixed allowlisted HTTPS endpoints, not a generic proxy. Node credentials stay in the local bridge process and are never sent to the frontend or public indexer. Loopback binding, exact Origin/Host checks, bounded requests, explicit methods, redirect rejection and separate broadcast confirmation reduce web-to-local attacks. Host/Origin/custom-header checks are browser-origin defenses, not client authentication. The public relay checks bounded transaction structure and transaction ID; without prevout data it cannot prove signatures or Ledger approval. The browser independently verifies signatures, and the upstream node performs consensus validation. The hosted website keeps account derivation in the browser. Its proxy receives queried addresses/transaction IDs and submitted signed transactions, not account derivation keys. The hosting operator can link requests with client IP/timing; the public indexer normally sees the proxy IP. A compromised website, browser extension or local machine can still mislead the UI or request a harmful payment; always compare the full address, amount and fee on the Ledger. No host-side label replaces trusted-device review.

## Sessions and recovery

PSBT/Merkle validation and ownership checks precede review. Approval authorizes the validated transaction commitments. The host invalidates its session after cancellation or a transport/protocol fault. Closing WebHID does not necessarily notify a still-powered device: reject any remaining review and exit/reopen the Pearl app before reconnecting. Historical device-side deadline, lock/power and nested-command tests apply only to their recorded artifacts. Current C-source Nano S Plus builds have passed bounded Speculos and real-regtest roundtrips; broader lifecycle/fault/device qualification remains incomplete. A connection failure is not proof that the device produced no partial signature. For an unchanged current initial attempt only, the app can release reservations if failure occurs before adapter signing is invoked, or after the adapter has fully unwound with no complete independently verified transaction returned to the app. Exact record/attempt ownership and absence of staged/persisted signed recovery are checked atomically. Complete results survive cancellation, final-ACK errors and persistence failures; historical/recovery/concurrently changed or broadcast-uncertain records remain reserved. This policy does not retrospectively clear old user records. Reopening an app and restoring a watch-only backup does not authorize a transaction.

## Stored data

The intended wallet flow never requests, obtains or stores Ledger seed material or private signing keys. Public-only import schemas reject unexpected fields; selecting an unrelated secret-bearing file would still read its bytes before rejection, so users must never choose seed/key files. The browser intentionally keeps origin-scoped payment journals, reservations, exact signed bytes and receive/change recovery ranges. Remembered public accounts and display caches contain public-key/chain-code metadata, but restore no device or spend-validation authority. Hosted functions keep no application account database or server wallet profile. This is financially sensitive data even though it cannot create a new signature. Anyone with an already-signed transaction can broadcast that exact transaction; backup files must remain private. Clearing storage can erase interrupted-payment history, so it is never used as an automatic recovery shortcut. The chain can reconstruct confirmed history but cannot reveal a transaction it has never received.

## Reporting

Until a public security contact is designated, report potential vulnerabilities privately to the repository owner. Do not post recovery material, device secrets, RPC credentials or exploit details publicly. Document an issue's affected commit, reproducible public test case, impact, expected behavior and actual behavior.

## Release gates

Current native scope and evidence are in [the C app](apps/ledger-bitcoin-prl/README.md), [build boundary](tools/bitcoin-prl-port/README.md) and [current C regtest roundtrip](tools/hosted-wallet-review/simulator/README.md). Historical native-release-qualification results describe the earlier Rust app and do not qualify the C signer. Source-bound builds and emulator checks apply only to each recorded source and artifact identity. Remaining gates include actual supported-device/retail-OS compatibility, physical screens/signing/restore and resource measurements, complete loaded-browser/IndexedDB flows, independent human and dependency review, Ledger vendor review, a production builder/distribution process and a selected project license. Software results and registry advisory scans do not establish these gates.
