# Mainnet trial

The intended next milestone is a user-run trial with approximately **10 PRL total**. The user supplies the funds and approves each real payment. This is a chosen test budget, not a hard wallet or consensus cap. Do not send funds to published fixture addresses or enter a recovery phrase in the companion.

## Current evidence and blocker

The current C app passed bounded Nano S Plus mainnet/regtest emulator tests, including P2TR/P2MR recipients and hostile-request rejection. One physical Nano S Plus on OS 1.7.0 passed account and Receive verification through Ledger Wallet; a separate HID pilot signed a synthetic nonexistent input. No real funds moved in those emulator/synthetic-signing checks. See [emulator evidence](../tools/live-app-native-review/README.md) and [physical evidence](../tools/live-app-physical-review/README.md).

**Incoming payment/confirmations were observed. The owner subsequently reported an outgoing mainnet submission; its UI/public-source state showed acceptance and pending own change. Destination confirmation has not yet been independently established.** The [local mainnet checkpoint](../tools/local-mainnet-review/README.md) records the actual Ledger Wallet account scan, a separate read-only local HTTP discovery/input-preflight check, an unsigned draft/discard, and background rescan with confirmation updates. No mainnet transaction was signed or broadcast during those checks. Local mode uses the native light client built from official Pearl wallet/Neutrino source. Hosted mode uses the fixed public indexer and retains a separate trust model; its [Vercel production deployment](../tools/hosted-wallet-review/release.md) passed public boundary/asset checks, which do not qualify outgoing mainnet signing or broadcast. Before any additional funding, require a completed account scan with active peers and matching wallet/header/filter state. An unavailable or incomplete balance must never be treated as zero or bypassed with a synthetic snapshot.

The current **Pearl 0.1.0** app was installed with owner approval on the recorded Nano S Plus OS 1.7.0, and account/Receive verification passed in actual Ledger Discover. Existing funds were unchanged. The [installation checkpoint](install-pearl.md) records the installed-app identity separately from ELF/HEX hashes. Earlier Pearl Dev evidence remains historical; no seed reset or device security change is needed.

## User-run sequence

1. Open the mainnet Pearl Live App and matching **Pearl** device app after its separately approved installation. Confirm the account, verify the complete receive address on Ledger, then copy it or use its verified QR.
2. After local synchronization and account scanning complete, send a small portion of the intended budget to that address from the user's existing wallet. Sync until the deposit appears and is spendable. Ordinary inputs need one confirmation; mining rewards need 100.
3. Prepare a small payment to an address the user controls. Review recipient, amount, total fee and any change on Ledger. Device approval produces a saved signed payment; use the separate **Send payment** action to broadcast it.
4. Record the transaction ID, verify its appearance in the destination wallet, and sync until confirmed. Keep the wallet backup private. If submission times out, check status and retry only the same saved transaction; do not release its reservations or prepare a replacement from those inputs.

A successful trial qualifies only the recorded app build, device/OS, transport, backend and transaction shape. It does not qualify other devices, maximum-input behavior, restoration or a release.

## Scope and trust

The supported profile is ordinary BIP86 P2TR owned inputs/change, one P2TR or P2MR recipient, at most 16 inputs and one change output, and SIGHASH_DEFAULT. Amounts and fees use integer grains. P2MR is recipient-only; XMSS, script-path custody, message signing, RBF and software-key import are excluded. The wallet deliberately has no pending-payment deletion action that forgets a signature or frees uncertain inputs.

The official desktop lite wallet starts a Pearl SPV wallet. The local companion now embeds its pinned wallet/Neutrino implementation in a watch-only native helper, including the official native verification libraries. Browser validation still checks raw transaction contents, ownership and response consistency. This inherits upstream SPV assumptions and does not establish full-node validation or independent qualification of every consensus path. Optional public-indexer mode retains its separate backend-trust model. Current everyday UI parity and remaining gaps are in the [feature matrix](prl-feature-coverage.md#current-desktoplite-parity).

Both modes calculate total fees automatically from exact size and the selected Fast/Medium/Slow rate (1/10/25-block targets), defaulting to fresh Medium. Max includes the selected fee; Custom accepts an explicit total. Quotes expire after 120 seconds; visible, idle, unprepared Amount screens refresh anonymous fees around 105 seconds. Fast/Medium/Slow show short approximate times of ≈3 min, ≈32 min and ≈1 h 21 min, derived from their 1/10/25-block targets and the pinned 194-second Pearl block target. These are rough target hints, not a countdown, measured current mining pace or confirmation guarantee. Equal-priced tiers remain separate choices. Unavailable estimates use a clearly labeled Standard relay-minimum fallback, never a promised confirmation speed. Activity currently lacks timestamps and general historical transaction fees. These are known parity limits, alongside bounded discovery and the 16-input signing cap.

The current C signer also passed the [16-check real Pearl regtest roundtrip](../tools/hosted-wallet-review/simulator/README.md): P2TR/P2MR recipient review, signature verification, rejection of a damaged witness, real node acceptance, mined confirmation and wallet refresh, using only the public fixture seed. This is current C-firmware evidence, separate from historical Rust tests. It does not replace the remaining owner-approved physical outgoing mainnet transaction.

A failed current initial signing attempt may release its inputs only before adapter signing is invoked, or after the adapter reports no complete verified app result, and only when atomic journal ownership checks pass. A partial signature is not a complete transaction. Complete results and older/recovery/broadcast uncertainty remain reserved; no historical record is cleared merely because the user recalls rejecting it. See [recovery policy](recovery.md).

Portfolio Balance includes all source-reported unspent owned outputs, including unconfirmed change. Send remains stricter: pending change cannot fund another payment until it has the required confirmation, and local reservations remain excluded from Send availability. No payment amount, recipient, transaction ID or wallet balance from the owner’s submission is published here.

Public-source pending monitoring now performs bounded visible/idle transaction checks and a fresh full scan only when a known status changes; it does not optimistically adjust the portfolio or retry a broadcast. Manual Refresh payment status also obtains fresh discovery first. Acceptance/pending change is still distinct from independently observed recipient confirmation.
